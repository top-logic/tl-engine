Design Section 2: Execution Engine

How background agents are triggered, executed, and how results flow

Core Component: BackgroundAgentExecutor

A single service that knows how to run any background agent through the pipeline. All trigger mechanisms (ChatProcessor, Scheduler, REST API) call into this one executor.

Execution Pipeline
┌──────────────────────────────┐ │ Trigger Sources │ │ │ │ ChatProcessor (post/pre) │ │ Scheduler (scheduled) │ │ REST API (on-demand) │ └──────────┬───────────────────┘ │ ▼ ┌──────────────────────────────┐ │ BackgroundAgentExecutor │ │ │ │ execute(agentName, context) │ │ │ │ 1. Resolve BackgroundConfig │ │ 2. Resolve InputAdapter │ │ 3. Gather input │ │ 4. Build UntypedAgent │ │ 5. Invoke agent │ │ 6. Parse result │ │ 7. Run OutputHandlers │ │ 8. Return AgentResult │ └──────────────────────────────┘ │ ▼ ┌────────────────────────────────────────┐ │ AgentResult │ │ │ │ status: PASS | ISSUE_FOUND | BLOCK │ │ message: "..." │ │ details: Map<String, Object> │ └────────────────────────────────────────┘

Input Adapters

InputAdapter Interface + Implementations
interface InputAdapter { /** Gather input and return the message to send to the agent. */ String gatherInput(BackgroundContext context); } ChatContextAdapter → Uses ConversationSerializer (already exists) → Config: content="last-turn" | "full-chat" → Only valid for scope=CHAT ScriptInputAdapter → Evaluates TLScript expression from config → Returns result as string → Works for both CHAT and APPLICATION scope AutonomousInputAdapter → Returns the configured trigger-message → Agent uses its tools to gather data → Most flexible, highest token cost ProviderInputAdapter → Delegates to configured Java InputProvider class → Most powerful, requires Java code → Provider receives BackgroundContext for access to KB, session, etc.

Output Handlers

OutputHandler Interface + Built-in Implementations
interface OutputHandler { /** Process the agent's result. Called after agent completes. */ void handle(AgentResult result, BackgroundContext context); } NotificationHandler → Pushes ReviewNotification to SSE stream (existing mechanism) → Config: severity="info|warning|error" AuditLogHandler → Writes to TopLogic audit/system log → Config: log-level="info|warn|error" SchedulerLogHandler (auto-added for scheduled agents) → Writes result to Scheduler's TaskLog → Visible in admin UI // Future handlers (not in v1): EmailHandler → sends email notification WebhookHandler → POST to external URL PersistenceHandler → stores result in KnowledgeBase

Concurrency & Debouncing

Execution Guarantees
Post-turn agents: → Run async in BACKGROUND_EXECUTOR (fire-and-forget) → Debounced per agent per session (max 1 concurrent per agent) → Failure isolated — never affects main chat Pre-turn agents: → Run synchronously BEFORE Orchestrator → Timeout configurable (default: 30s) → On timeout → treat as PASS (fail-open) or BLOCK (fail-closed) → Configurable: fail-policy="open|closed" Scheduled agents: → Managed by TopLogic Scheduler (maxTask concurrency limit) → Cluster-aware (run on one node or all) → Graceful stop/kill via Scheduler infrastructure → Result visible in Scheduler admin UI On-demand agents: → Run async, result returned via SSE or polling → Optional: REST endpoint returns result synchronously
