# Edit mode with a working copy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the configuration editor an edit mode that works on a copy, checks the configuration before letting the copy through, and reports every violation at the field that caused it.

**Architecture:** A new `ConfigFormControl` wraps a `ConfigEditorControl` and owns the mode. Entering edit mode copies the item with `TypedConfiguration.copy` and rebuilds the editor over the copy; Apply validates and, only if the copy is clean, writes its content back into the original; Cancel drops the copy. `ConfigEditorControl` itself is unchanged in its write-through behaviour - it never learns about the mode, which is what lets the view designer and every nested editor keep using it exactly as today. To put a violation at its field, the editor reports every field model it builds to an optional `ConfigFieldIndex`, keyed by the item and property it edits.

**Tech Stack:** Java, TopLogic TypedConfiguration (`TypedConfiguration.copy`, `ConfigCopier`, `ConstraintChecker`), the React view layer (`ReactControl`, `ReactButtonControl`, `ReactFormLayoutControl`), JUnit 3-style tests under `test.com.top_logic.layout.configedit`.

**Spec:** `docs/superpowers/specs/2026-08-12-config-form-element-design.md`, section 3 ("Edit mode, working copy, validation")

## Task 1: The field index

**Files:**
- Create: `com.top_logic.layout.configedit/src/main/java/com/top_logic/layout/configedit/ConfigFieldIndex.java`
- Test: `com.top_logic.layout.configedit/src/test/java/test/com/top_logic/layout/configedit/TestConfigFieldIndex.java`

**Interfaces:**
- Consumes: nothing.
- Produces: `ConfigFieldIndex` with
  `void register(ConfigurationItem item, PropertyDescriptor property, ConfigFieldModel model)`,
  `ConfigFieldModel lookup(ConfigurationItem item, PropertyDescriptor property)`,
  `void clear()`.

Why an index at all: a violation names an item and a property (that is what `ConstraintFailure` carries), but the field that shows it is a `ConfigFieldModel` buried in the control tree. Nothing today can get from the one to the other. The index is filled while the editor builds and read when Apply refuses.

Identity, not equality, is the key on both halves. Two configuration items are equal only if they are the same object, and `PropertyDescriptor` overrides neither `equals` nor `hashCode` - and a subtype's descriptor hands out its own instance even for an inherited property. An `IdentityHashMap` keyed by the item, holding an `IdentityHashMap` keyed by the property, says exactly that and cannot drift.

```java
public final class ConfigFieldIndex {

    private final Map<ConfigurationItem, Map<PropertyDescriptor, ConfigFieldModel>> _fields =
        new IdentityHashMap<>();

    public void register(ConfigurationItem item, PropertyDescriptor property, ConfigFieldModel model) {
        _fields.computeIfAbsent(item, any -> new IdentityHashMap<>()).put(property, model);
    }

    public ConfigFieldModel lookup(ConfigurationItem item, PropertyDescriptor property) {
        Map<PropertyDescriptor, ConfigFieldModel> byProperty = _fields.get(item);
        return byProperty == null ? null : byProperty.get(property);
    }

    public void clear() {
        _fields.clear();
    }
}
```

Both maps are `IdentityHashMap`, and the class doc must say why: configuration items are identity-equal anyway, but `PropertyDescriptor` has no `equals`/`hashCode` of its own, so a hash map would already behave this way by accident. Saying it outright keeps a later `HashMap` from looking harmless.

The target is a parameter rather than always `original()` so that a caller with its own recipient can name it.

```java
public final class ConfigFormModel {

    private final ConfigurationItem _original;

    private ConfigurationItem _copy;

    private final List<Runnable> _listeners = new ArrayList<>();

    public ConfigFormModel(ConfigurationItem original) {
        _original = original;
    }

    public ConfigurationItem original() {
        return _original;
    }

    public ConfigurationItem edited() {
        return _copy != null ? _copy : _original;
    }

    public boolean isEditMode() {
        return _copy != null;
    }

    public void startEditing() {
        _copy = TypedConfiguration.copy(_original);
        notifyListeners();
    }

    public void applyTo(ConfigurationItem target) {
        ConfigCopier.copyContent(new DefaultInstantiationContext(ConfigFormModel.class), _copy, target, true);
        _copy = null;
        notifyListeners();
    }

    public void cancelEditing() {
        _copy = null;
        notifyListeners();
    }

    public void addListener(Runnable listener) {
        _listeners.add(listener);
    }

    public void removeListener(Runnable listener) {
        _listeners.remove(listener);
    }

    private void notifyListeners() {
        for (Runnable listener : new ArrayList<>(_listeners)) {
            listener.run();
        }
    }
}
```

`notifyListeners` iterates a copy of the list: a listener that rebuilds the editor may well add or drop listeners of its own while it runs.

  plus `record Violation(ConfigurationItem item, PropertyDescriptor property, ResKey message)`.

Two kinds of violation, from two different places:

- A **mandatory property with no value**. `PropertyDescriptor#isMandatory()` says it is required; `ConfigurationItem#valueSet(PropertyDescriptor)` says whether it has been given one. This is not something `ConstraintChecker` reports - the configuration framework catches a missing mandatory value when it reads XML, and nothing reads XML here.
- A **constraint violation**, from `ConstraintChecker`. It is recursive, so one call covers nested items and collection entries, and every `ConstraintFailure` already names the item and the context property - exactly the pair the index is keyed by. Warnings (`ConstraintFailure#isWarning()`) are not violations and must not block Apply.

`report` returns whether every violation found a field. One that did not is a real possibility - a violation on a property the editor does not render, say - and swallowing it would leave Apply refusing with nothing on screen to explain why. The caller uses the answer to decide whether it also needs to say something at the form level.

```java
public final class ConfigValidation {

    /** One reason the configuration may not be applied, and where it belongs. */
    public record Violation(ConfigurationItem item, PropertyDescriptor property, ResKey message) {
        // Nothing beyond the components.
    }

    private ConfigValidation() {
        // Static use only.
    }

    public static List<Violation> check(ConfigurationItem item) {
        List<Violation> violations = new ArrayList<>();
        collectMissingMandatory(item, violations, Collections.newSetFromMap(new IdentityHashMap<>()));
        collectConstraintFailures(item, violations);
        return violations;
    }

    public static boolean report(List<Violation> violations, ConfigFieldIndex index) {
        boolean complete = true;
        for (Violation violation : violations) {
            ConfigFieldModel field = index.lookup(violation.item(), violation.property());
            if (field == null) {
                complete = false;
            } else {
                field.setError(violation.message());
            }
        }
        return complete;
    }
}
```

`collectMissingMandatory` walks the item and every nested item and collection entry reachable through its ITEM, LIST, ARRAY and MAP properties, guarding against revisiting an item it has already seen - a configuration may well hold the same item twice, and a cycle would otherwise not terminate. For each visited item, every property with `property.isMandatory() && !visited.valueSet(property)` becomes a `Violation` carrying
`I18NConstants.ERROR_VALUE_REQUIRED__PROPERTY.fill(Labels.propertyLabel(property, false))` - the message the field already uses for the same thing, so a refused Apply and a rejected keystroke read alike.

`collectConstraintFailures` runs the checker and reads its failures:

```java
ConstraintChecker checker = new ConstraintChecker();
try {
    checker.check(item);
} catch (ConfigurationException ex) {
    // Malformed constraint annotations - a programming error in the configuration interface, not
    // something the user editing the form did or can fix. Nothing is added; the constraints that
    // did parse have already been collected.
    Logger.error("Cannot check constraints of '" + item + "'.", ex, ConfigValidation.class);
}
for (ConstraintFailure failure : checker.getFailures()) {
    if (!failure.isWarning()) {
        violations.add(new Violation(failure.getItem(), failure.getContextProperty(), failure.getMessage()));
    }
}
```

Use this overload, `check(ConfigurationItem)`, and not `check(Log, ConfigurationItem)`: the logging overloads clear the failure list in a `finally` block, so reading `getFailures()` after one of those gives an empty list every time. The throwing overload leaves the failures in place, which is what makes them readable at all.

`Logger` is `com.top_logic.basic.Logger`.

```java
public class ConfigFormControl extends ReactFormLayoutControl {

    private final ReactContext _context;

    private final ConfigFormModel _model;

    private final boolean _withEditMode;

    private final ConfigFieldIndex _index = new ConfigFieldIndex();

    public ConfigFormControl(ReactContext context, ConfigurationItem config) {
        this(context, config, true);
    }

    public ConfigFormControl(ReactContext context, ConfigurationItem config, boolean withEditMode) {
        super(context);
        _context = context;
        _model = new ConfigFormModel(config);
        _withEditMode = withEditMode;
        rebuild();
    }

    private void rebuild() {
        for (ReactControl child : getChildren()) {
            child.cleanupTree();
        }
        getChildren().clear();
        _index.clear();

        addChild(new ConfigEditorControl(_context, _model.edited(), Collections.emptySet(), false, _index));

        if (_withEditMode) {
            addChild(_model.isEditMode() ? applyAndCancel() : editButton());
        }

        putState("children", getChildren());
    }
}
```

`_index.clear()` before rebuilding, and nowhere else: every render cycle creates fresh field models, and a stale one would take an error nobody can see.

Apply:

```java
private void apply() {
    List<Violation> violations = ConfigValidation.check(_model.edited());
    if (!violations.isEmpty()) {
        ConfigValidation.report(violations, _index);
        return;
    }
    _model.applyTo(_model.original());
}
```

Refusing returns without touching the mode - and without rebuilding, since a rebuild would discard the very fields the errors were just put on.

The three buttons are `ReactButtonControl`s whose handlers call `startEditing()`, `apply()` and `cancelEditing()`; the model's listener calls `rebuild()`, so the two mode-changing ones need no rebuild of their own. Register that listener in the constructor and remove it in `onCleanup()`.
