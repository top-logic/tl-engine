# Development rules for the AI modules

## Project structure

The modules follow the engine's layout. Package roots:

| Module | Base package |
|---|---|
| `tl-ai-tool-api` | `com.top_logic.tl.ai.tool.api` (+ `.registry`) |
| `tl-ai-core` | `com.top_logic.tl.ai.core.*` (`agent`, `provider`, `tools`, `message`, `memory`, `mcp`, `session`, `scripting`, `security`, `citation`, `limits`, `cost`, `observe`, `access`, ...) |
| `tl-chat` | `com.top_logic.ai.chat.*` (`api`, `layout`, `history`, `sched`) |
| `tl-chat-classic` | `com.top_logic.ai.chat.classic` |
| `tl-ai-mcp-server` | `com.top_logic.ai.mcp.server.*` (`tools`, `resources`, `dynamic`, `completions`, `authentication`) |
| `tl-ai-a2a` | `com.top_logic.ai.a2a.*` (protocol, server, client) |
| `tl-ai-views` | `com.top_logic.ai.views` |
| `tl-ai-vector-index` | `com.top_logic.ai.vector.index.*` |
| `tl-ai-index`, `tl-ai-index-onnx` | `com.top_logic.tl.ai.index.*` |
| `tl-ai-eval` | `com.top_logic.tl.ai.eval` |

Configuration files per module:

- model definitions: `src/main/webapp/WEB-INF/model/tl.ai.<module>.model.xml`, with their auto-configuration `src/main/webapp/WEB-INF/autoconf/model.tl.ai.<module>.config.xml`;
- application configuration: `src/main/webapp/WEB-INF/conf/tl-ai-<module>.conf.config.xml` (and `tl-ai-<module>.conf.xml` for aliases);
- servlet registration through `web-fragment.xml` in `src/main/resources/META-INF/`.

How tests are placed and run is described in [testing](doc:ai/testing).

## Resource keys

- `messages_en.properties` is generated by the build's doclet from the `@en` JavaDoc tags - never edit it by hand (see [the i18n article](doc:i18n)).
- **Write both `@en` and `@de` on every `ResKey` constant, and copy the `@de` text verbatim into the module's `messages_de.properties`.** No generator reads `@de`: the doclet exports `@en`, and the build's translation machine-translates from that English alone - for a key with no German yet and for a key whose English changed since the last build, so rewording an `@en` text replaces the hand-written German of that key. `@de` is the authored source of truth, and `messages_de.properties` is maintained by hand. Adding a resource key is therefore three edits: `@en` on the constant, `@de` on the same constant, and the same German text in `src/main/java/META-INF/messages_de.properties`.
- The guard is `TestGermanResourcesMatchJavaDoc`. It walks every AI module of the reactor, so run it once from `tl-ai-core` whichever module changed:

  ```bash
  mvn test -DskipTests=false -pl tl-ai-core -Dtest=test.com.top_logic.tl.ai.core.TestGermanResourcesMatchJavaDoc
  ```

  It fails when a documented constant has no `@de`, when the shipped German is not the `@de` text, when a `@de` text reaches no bundle, and when a bundle holds a `[missing:...]` generator placeholder.
- Labels and tooltips of configuration properties have no `@en` / `@de` mechanism: the doclet derives them from the JavaDoc prose and the German stays machine-translated, so read it after adding a configuration option.

### Text for the model and text for people

**A tool's answer to the model is no `ResKey`** - its result text, its refusal, its `@ToolMethod` description. Those are English literals next to the code that writes them (`TidDiagnostics`, `ToolResults`, `PresentTool`, every tool in `tools/`), because they are read by the model rather than by the user: translating them would make what a run does depend on who started it. The exception is text that is *about* the user and is meant to reach them through the model - the wording of the environment block (`tl.ai.environment.template`) is a translated resource for that reason. Text a **person** reads - a label, a command, an error in the UI - follows the resource-key rule above.

## Code

- **No hand-written POJO DTOs** - data transfer objects are msgbuf `.proto` messages (see [msgbuf](doc:engine/msgbuf) and the `create-dto` skill), and JSON is read and written with msgbuf's `JsonWriter` / `JsonReader`, not with Jackson's `ObjectMapper`.
- **No `@author` tags** in JavaDoc; the history is in git.
- **Configuration property constants** carry an `@see` pointing to their getter (see the `toplogic-service` skill).
- **Service start-up errors** are `RuntimeException`s; `ConfigurationError` only for errors a user acts on.
- **All LLM providers stream** - there are no blocking request/response calls.
- **Services** are TopLogic `ConfiguredManagedClass` singletons with a `Module`: `LLMProviderService`, `AgentRuntimeService`, `ToolRegistryService`, `McpServerRegistry`, `AiToolAccessService`, ...
- **Run state that code beneath a tool needs** travels in thread-local bindings bound around the call - `RunInfoBinding`, `TaskStoreBinding`, `UserInteractionStoreBinding`, `ConversationLogListenerBinding`, `LoadedSkillsBinding`, `UserMemoryBinding` - on the thread the tool actually runs on.
- **Reflection-based tools** rely on the compiler option `parameters=true`, which the engine's parent POM sets.
- A new entry point of an agent run builds its `SecurityContext` through `RunSecurity.contextFor(RunPrincipal)`, never `TopLogicSecurityContext` directly, or the installation's `<security-context>` factory is skipped - see [approval from the call](doc:ai/security/administration#approval-decided-from-the-call).
- HTML is made from model text only through `Converters.markdownToHtmlString` - see [rendering the answer](doc:ai/security/output-guard-and-audit#rendering-the-answer).
- Sources are UTF-8, and tests are JUnit tests on the `TestCase` base class.
