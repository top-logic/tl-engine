How should application-scoped background agents get their input?

Three approaches with concrete examples — click the one that fits best

A

Configurable Input Providers (Java plugin)

Each background agent declares an InputProvider — a Java class that gathers data and returns it as a string for the agent to process.

Config XML
<agent name="SecurityAuditor"> <background trigger="scheduled" cron="0 0 * * *"> <input-provider class="com.top_logic.ai.service .bg.input.ModelSnapshotProvider"> <module-filter>myApp</module-filter> <include-instances>true</include-instances> </input-provider> </background> </agent>

Pros

  • Full power of Java — can query KB, call APIs, aggregate complex data
  • Type-safe, testable, reusable across agents
  • Can pre-filter/optimize data before sending to LLM

Cons

  • Requires Java code for each new input source
  • Heavier to add — needs compile, deploy
  • More coupling between agent config and Java classes

Example agents:

  • SecurityAuditor — ModelSnapshotProvider dumps current model state for compliance review
  • DataQualityChecker — InstanceQueryProvider queries all instances of a type and feeds them for validation
  • AuditLogReviewer — AuditLogProvider reads last 24h of audit entries
B

TLScript-based Input (no-code)

The agent's input is a TLScript expression defined in XML config. The framework evaluates it and passes the result as the agent's message.

Config XML
<agent name="SecurityAuditor"> <background trigger="scheduled" cron="0 0 * * *"> <input-script> all(`myApp:SensitiveRecord`) .filter(r -> r.get(`lastReview`) == null || daysBetween(r.get(`lastReview`), now()) > 30) .map(r -> r.get(`name`) + ": " + r.get(`accessLevel`)) .toString("\n") </input-script> </background> </agent>

Pros

  • No Java code needed — pure configuration
  • Fast iteration — change script, restart, done
  • Leverages existing TLScript ecosystem (model-aware)
  • Very TopLogic-native

Cons

  • Limited to what TLScript can express
  • Complex data gathering can get messy in XML
  • Harder to test in isolation
  • Script output is always a string — no structured pre-processing

Example agents:

  • SecurityAuditor — TLScript queries unreviewed sensitive records
  • ModelConsistencyChecker — TLScript finds types without descriptions
  • StaleDataDetector — TLScript finds records not updated in 90 days
C

Tool-based Self-Service (autonomous)

The agent is invoked with just a trigger message (e.g. "Run your daily security check"). It uses its own configured tools to gather whatever data it needs — just like the Orchestrator uses tools to answer user questions.

Config XML
<agent name="SecurityAuditor" tools="tl.listInstances,tl.listTypeParts, tl.executeTLScript,gitea.create_gitea_issue"> <background trigger="scheduled" cron="0 0 * * *"> <trigger-message> Run your daily security audit. Check all SensitiveRecord instances for compliance. </trigger-message> </background> </agent>

Pros

  • Simplest framework — agent is just an agent with tools
  • Most flexible — agent decides what to look at
  • No new abstractions (InputProvider, TLScript eval)
  • Agent can adapt its strategy based on what it finds
  • Consistent with how conversational agents already work

Cons

  • More LLM calls (agent must tool-call to gather data)
  • Higher token cost per execution
  • Less predictable — agent might not check everything
  • Harder to guarantee completeness of checks

Example agents:

  • SecurityAuditor — uses listInstances + executeTLScript tools to find and analyze records
  • ModelValidator — uses model browser tools to check naming conventions
  • SystemHealthMonitor — uses custom health-check tools to verify services

Or combine them?

These aren't mutually exclusive. The framework could support all three as different input-mode values:

  • input-mode="provider" → Java InputProvider class
  • input-mode="script" → TLScript expression
  • input-mode="autonomous" → Just a trigger message, agent uses tools

Each agent picks what fits its use case. A simple model checker uses TLScript, a complex compliance audit uses a Java provider, and an exploratory agent goes autonomous.
