Architectural Approaches

Three ways to structure the Background Agent Framework — click the one you prefer

A

Unified Pipeline Architecture (Recommended)

A single BackgroundAgentPipeline that all background agents flow through: Input → Agent → Output. Each stage is pluggable.

Pros

  • Single abstraction covers all patterns
  • Each stage is independently pluggable
  • New trigger/input/output types don't require framework changes
  • Clean separation of concerns

Cons

  • Pipeline overhead for simple cases (ReviewAgent just needs trigger → agent → log)
  • More interfaces to implement upfront
B

Event-Driven Architecture

Background agents subscribe to events (turn-completed, turn-starting, timer-fired, manual-trigger). An event bus dispatches to registered agents.

Architecture
┌───────────────────────────────────────────┐ │ BackgroundAgentEventBus │ │ │ │ Events: │ │ ├─ TurnCompletedEvent (chat context) │ │ ├─ TurnStartingEvent (chat context) │ │ ├─ ScheduledEvent (timer context) │ │ ├─ ManualTriggerEvent (API context) │ │ └─ ApplicationEvent (custom context) │ │ │ │ Subscriptions: │ │ ├─ ReviewAgent → TurnCompletedEvent │ │ ├─ SecurityGate → TurnStartingEvent │ │ ├─ ComplianceBot → ScheduledEvent │ │ └─ AuditAgent → TurnCompleted + Sched. │ └───────────────────────────────────────────┘

Pros

  • Very flexible — agents can subscribe to multiple events
  • Loosely coupled — agents don't know about each other
  • Easy to add new event types

Cons

  • Pre-turn interception is awkward in event model (needs sync blocking)
  • Event bus is a new infrastructure piece to maintain
  • Harder to reason about execution order
  • Doesn't leverage TopLogic Scheduler naturally
C

Interceptor Chain (Servlet Filter Pattern)

Background agents are organized as a chain of interceptors around the main agent. Pre-turn agents run before, post-turn after. Scheduled agents are separate.

Architecture
User Message │ ▼ ┌──────────────┐ │ SecurityGate │ PRE-TURN (can block) └──────┬───────┘ ▼ ┌──────────────┐ │ ContentFilter │ PRE-TURN (can modify) └──────┬───────┘ ▼ ┌──────────────┐ │ Orchestrator │ MAIN AGENT └──────┬───────┘ ▼ ┌──────────────┐ │ ReviewAgent │ POST-TURN (observe) └──────┬───────┘ ▼ ┌──────────────┐ │ AuditLogger │ POST-TURN (observe) └──────┬───────┘ ▼ Response to User (Scheduled agents run separately via Scheduler)

Pros

  • Very intuitive mental model (like servlet filters)
  • Clear execution order
  • Pre-turn blocking is natural

Cons

  • Only works for chat-scoped agents — scheduled agents need a separate mechanism
  • Tight coupling to conversation flow
  • Two different systems for chat vs application scope

My Recommendation: A (Unified Pipeline)

Approach A handles all four lifecycle patterns uniformly. The pipeline stages map cleanly to what we discussed:

  • Trigger = lifecycle pattern (post-turn, pre-turn, scheduled, on-demand)
  • Input = combined input modes (provider, script, autonomous, chat-context)
  • Agent = standard LangChain4j agent from AgentRegistry (same as today)
  • Output = OutputHandlers (notification, audit, email, etc.)
  • Authority = advisory vs authoritative (only meaningful for pre-turn)

Scheduled agents naturally integrate with TopLogic's Scheduler via a BackgroundAgentTask that extends StateHandlingTask. Chat-scoped agents are triggered from ChatProcessor the same way ReviewAgent is today, but generalized.
