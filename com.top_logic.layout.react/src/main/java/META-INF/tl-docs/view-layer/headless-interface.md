# The headless interface

The browser sees a React window as a tree of controls whose state the server sends and to which it sends commands back. The headless interface (`com.top_logic.layout.react.scripting`) makes the same tree usable without a browser: a consumer reads the display as an addressable tree, picks a node by a semantic address and dispatches a command to it. There is no second implementation of behavior: acting dispatches through `ReactControl.executeCommand`, the method the browser's commands reach as well.

Its consumers are

- the **script recorder**, which captures the commands a user's interactions dispatch as replayable steps, and the replay of such a script (the recorder side-window and the UI inspector of `tl-layout-view`);
- **agents**: in-process (the page tools of `tl-ai-views` read and rebuild a window through it) or outside the server through the HTTP endpoint of the optional module `tl-layout-view-agent`.

The interface is in-process; reaching it from outside is a matter of its own with its own admission rules, which is why the HTTP surface is a module of its own.

## Observe, resolve, act

`ScriptingSession.forRoot(queue.getRootControl())` opens a session on the window's displayed root (the root `ViewServlet` sets on the window's `SSEUpdateQueue`). Controls registered in the queue but no longer reachable from that root are not part of it.

- `observe()` projects the tree into a `ScriptingNodeView`: the synthetic root `/` (role `app`) with the window's top-level nodes as children. Each node carries `address`, `role`, an optional `name`, its React `module`, its `state`, the `actions` it offers and its `children`. `observeJson()` renders it as JSON (`ScriptingNodeView.toMap()`): the argument schemas of the actions are listed once, in the member `schemas` of the root by their `ArgsSchema` id, and an action taking arguments refers to its schema by `"argsSchema": {"$ref": "#/schemas/<id>"}`. Both take an optional `ProjectionMode`, see [Object ids and keys](#object-ids-and-keys); without one they project for an agent (`AGENT`).
- `observeActionsJson()` is the compact view for an agent loop: `{"actions": [...]}`, a flat list of only the nodes that offer actions, without children, with the same addresses. `observeActions()` returns the same as a `Map`; it lists the schemas of its actions in its own `schemas` member.
- For a large observation, render without an intermediate string: `ScriptingNodeView.writeJson(Appendable)` streams the indented JSON of `toJson()` into a writer, and `ScriptingNodeView.writeValue(JsonWriter, Object)` writes the `toMap()` of a node (or the map of `observeActions()`) as a member of an enclosing document.
- `resolve(address)` maps an address back to the live control; an address that does not resolve throws `IllegalArgumentException` naming the segment that was not found and the segments that are available. `resolveNode(address)` resolves to a node of the projection, which may also be an item (see [What the observation contains](#what-the-observation-contains)).
- `act(address, command, arguments)` resolves the address and dispatches the command through `ScriptingSession.execute(control, address, command, arguments)`, returning the reply of the command's handler (a msgbuf message, `null` for none, see `ReactCommandHandler` and `ReactCommandAnswer`) and throwing its failure. `execute` refuses a command the control does not have at all with a message in the user's language naming the command and the address, and a command the control does not offer (see [Acting is acting as the user](#acting-is-acting-as-the-user)); every headless dispatch - `act`, `replay`, the agent endpoint - goes through it.
- `addressOf(control)` is the reverse of `resolve`: it walks the projected tree with the same segment algorithm, so its result resolves back to the control. It addresses an item by the key of its object, so the address is replay-stable. It is `null` for a control that is not part of the projection (a read-only cell control, a hidden control, a control inside an elided wrapper).

## What the observation contains

The observation shows what a user sees and can operate, no more. The pruning happens in one place, `ScriptingTreeProjector.children(node)`, which asks the controls and never switches on their types:

- **Invisible controls are omitted with their subtree.** `scriptingVisible()` is `false` for a control the user does not see: by default a `hidden` control (`setHidden`), further a form field whose chrome is `visible: false`, a closed menu, a snackbar or notice bar without a message, a notice bar restricted to the last moments before its deadline (`setLeadMillis`, the session timeout) while more than that lead time remains. A container leaves out the children it renders but does not show through `visibleChildren()`, the default of `scriptingChildren()`: the tile stack its covered frames, the accordion and the form group (`ReactFormGroupControl`) the content of a collapsed section - the group node stays, with `collapsed: true` and its `toggleCollapse` action -, and a form (`FormControl`) its fields while it shows its `noModelMessage` because it has no object.
- **Only executable actions.** An action is advertised only while `scriptingCommandState(command)` is executable: no `click` on a hidden or disabled button, no `valueChanged`, `commit`, `submit` (or other input command) on a field that does not accept input (`ReactFormFieldControl.scriptingDisplayCommands()` names the commands a field offers in view mode, such as `goto` of a dropdown whose value carries a link), no `resetValue` on a read-only field, no `selectItem` on a closed menu, no `goto` on a resource cell without a link, no `addRow` on a row-set table outside edit mode, the form lifecycle commands only in their edit state.
- **Items of a container.** A table, a tree and a board describe their rows, nodes and cards in their own state (`rows` with the cell texts, `nodes` with the labels, `columns` with the cards). The controls they display for a row, node or card are their `scriptingItems()`, not their `scriptingChildren()`: such a control is projected only if the user can operate it (it, or a node below it, offers an executable action) - an editable field in edit mode, an enabled button or link -, under a node of its item: `/…/tableView/row[v12]/button[Open]`, `/…/treeView/node[v7]/resourceCell[Alpha]`, `/…/kanbanBoard/card[v40]/button[Details]`. The item node has the role of the item (`row`, `node`, `card`), the label of its object as name, and its identity as state (`id` and `label` in `AGENT` mode, `key` in `KEY` mode). A read-only cell control - display text, a read-only field, a node label without a link - is no node; the row's `cells` and the tree's `nodes` carry its text. A row or node without operable content has no node.

An item segment holds the id of the item (the row, node or card id the commands take) in the `AGENT` observation and the business key of its object - JSON with `%`, `/`, `[`, `]` and `#` percent-encoded, `ScriptingTreeProjector.keyArgument` - in the `KEY` projection and in `addressOf`; `resolve` accepts both. A recorded click on the button of a row therefore names the row by its key and replays on the button of the same object's row in another session.

All of this reads and changes the live control tree of a window. It therefore runs inside the window's subsession and within an `Interaction` of the session (`ReactWindowRegistry.beginInteraction()`, the session's request lock), exactly like a command from the browser. After acting, `ReactWindowRegistry.synthesizeModelEvents(windowName)` lets derived state settle before the next observation, so a headless caller reads a settled state instead of waiting for SSE delivery. `ReactWindowReplay.inWindow(registry, windowName, action)` and `ReactWindowReplay.act(registry, windowName, step)` do all of this for a window other than the one the current request belongs to (installing that window's subsession, running in an interaction, synthesizing the window's model events before the action - so that it sees the commits other threads made, as a command of the window's page does - and after it, restoring the caller's subsession); the updates the command produces go to the target window's SSE connection, so the effect appears in that browser window.

## Addresses

An address is a `/`-separated path of segments, one per projected ancestor: `/appShell/sidebar/item[attributes]/tabBar/tab[table]/table[Demo]`. A segment is built from the node's role and an optional name discriminator, `role[name]`.

- **Role.** `ReactControl.scriptingRole()`, or derived from the React module (`TLButton` becomes `button`, `TableView` becomes `tableView`).
- **Name.** In this order: `ReactControl.scriptingName()` - the empty string addresses the control by its role alone, as a calendar (titled by the range it shows) and a flow diagram (whose model is its whole content) do -; the first non-empty string of the state keys `name`, `label`, `title`, `text`; the label of the control's model (`MetaLabelProvider`). A label that is a default `Object.toString()` (`Something@1a2b3c`) is no name. The name is reduced to letters, digits, `_` and `-` (blanks become `_`).
- **Siblings.** Siblings with the same segment get an occurrence index: `row#0`, `row#1`. Such an index depends on the order of the siblings and is the weakest part of an address; a name that tells siblings apart avoids it.
- **Transparent wrappers.** A control whose `scriptingTransparent()` is `true` (stacks, insets, split panels, slot placeholders, reload boundaries) is elided, its children are lifted into its parent. This keeps addresses short and stable against layout refactorings.
- **Navigation slots.** A container that shows content selected by the user addresses that content by the stable configuration id of the selected entry: `scriptingChildSlot(child)` returns `ScriptingControl.slotSegment(role, id)` - the sidebar `item[<nav item id>]`, the tab bar `tab[<tab id>]`, the deck pane `pane[<index>]`. The content's address thereby names the navigation context it belongs to. The container's own address does not change with its selection, and an address recorded under one selection fails to resolve under another, instead of hitting a look-alike control of another context. A slotted child is never elided as transparent.

An address derives from roles, names and the shape of the tree, never from the per-session control ids (`v17`), so it resolves in another session as long as the view structure is the same. A drifted address fails loudly; there is no fuzzy best match. Finding another way is up to the consumer.

## Identities of business objects

A row of a table, a node of a tree, an option of a select or an item of a selectable list is identified, across sessions, not by its position or a session-allocated id but by its business object. `ScriptingModelKey.toKey(context, object)` builds a `ModelName` for the object - the object naming of the classic script recorder, with its `ModelNamingScheme`s - and the `KEY` projection carries it as `key`, written as configuration JSON. The commands themselves take the session-bound id of an object (see "Object ids and keys"); a key reaches a command only through a recorded step, whose replay translates it back into the id.

**The projection carries no session-bound id for an object that has a key.** `ScriptingModelKey.putIdentity(projection, context, object, idProperty, id)` puts the `key` of an object, and its session id under `id` only if the object has no name, dropping `idProperty`, the property the client state carries the id in; `ItemSelection.identifyItem` / `identifyItems` / `identifyKeys` do the same for the client keys of a selectable list or board. So the tree projects its displayed `nodes` (`key`, `depth`, `expandable`, `expanded`, `selected`), the table the `rows` of its viewport (`key`, `selected`, the cell texts), the dropdown its `options` and its `value`, the selectable list its `itemKeys` (an entry per item) and `selected`, the board its `columns` (`key`, `label`, `count`, `cards` with an entry per card) and `selected`, each by key. A recorded assertion on that state holds in every session. A masked dropdown value is projected with its placeholder label and `masked: true` only - never its identity, and its id only in the `AGENT` projection, so an agent setting the value can keep it. Client wiring that names other controls or client-side ids (`dropVerdicts`, the drawer toggle's `controls`, the menu region's `childId`) and the table's keyboard cursor are presentation keys and not projected.

- A name is resolved by `ModelResolver` in a `ReactActionContext`, an `ActionContext` carrying only the `DisplayContext` and the session. Its `getMainLayout()` throws: a naming scheme that needs the component tree of the classic UI does not apply in the React view layer.
- `ReactOptionByLabelNaming` names an option by its label relative to its select control (`ReactOptionScope`), so the label only has to be unique among the options of that control. Where two options share a label, the scheme declines and the global scheme names the object instead, so identity is never lost.
- The default global naming is by label (`TLObjectByLabelNaming`): in most models the label is the business identifier, and unlike a database id it survives a fresh database, which is what a recorded test runs against.
- A control resolving a recorded key that names no row, node or option fails the command with a message; it never substitutes another object or drops the key silently.

## Object ids and keys

A control whose commands take the objects it displays by id offers `ObjectIdentities` through `objectIdentities()` (the default `null` offers none). The ids come from an `ObjectIdIndex`: an object keeps its id while it stays in the index, resolvable in both directions; `ItemSelection` keeps its client keys in one. The tree indexes its displayed nodes - the nodes, not their objects, so an object shown at two places has two ids -: `select {nodeId, ctrlKey, shiftKey}`, `expand {nodeId}`, `collapse {nodeId}`, `activate {nodeId}` and `contextMenu {nodeId, x, y}` take the id of a displayed node, recorded as the global key of the node's object; a key resolves to the first displayed node of its object in display order, and only to a node whose ancestors are all expanded - expanding them is a step of its own. The table indexes its displayed rows by their row keys, handing a row its id when it first sends, projects or looks it up, and dropping the ids of the rows that leave the view whenever the rows change: `select {rowId, ctrlKey, shiftKey}`, `activate {rowId}` and `expand {rowId, expanded}` take the id of a displayed row, which stays the same while the rows are sorted, filtered or regrouped around it, so a gesture never hits another row than the one it was made on. A key resolves among the rows of the current view - also those outside the client's viewport, but not those inside a collapsed group or tree row or hidden by the filter - to the first row of its object; a group header has no key, so a gesture on it is recorded with its id. The client lays the rows out by their positions (`index`, `selectedRows`, `cursorIndex`); the row at the cursor is sent as `cursorId` for the keyboard gestures on it. `moveSelection` and `selectAll` take no row. A selectable list offers the identities of its `ItemSelection`, a board those of its cards and its columns (`CombinedIdentities`): `selectItem {key}` and `selectCard {card}` take the client key of an item or card, recorded as the global key of its object, a drop on a board names a card or a column by its client key, and a key resolves only to a displayed item, card or column. The dropdown indexes its options and the elements of its value, adding an option when it first describes or resolves it, so an option list that is never opened costs no ids; its keys are built relative to its `ReactOptionScope` and resolve among all its options and its value, not only those the client has loaded. The identities translate an id into the business key of its object (`keyOf`, relative to the control's `keyContext()`) and a key back into the id the object has now (`idOfKey`), resolving only among the objects the control has at hand - it never expands or scrolls anything into view.

A property of a typed argument interface carrying such an id (a `String`, or a `List<String>`) is marked `@DisplayedObjectId`. The recorder replaces each marked id by the key of its object, the `ModelName` as JSON, in the same property (an object without a key keeps its id); the replay resolves the key back through the identities of the target control and dispatches the command with the id, failing with "The object is not displayed" if the object is not at hand. The description of a recorded step renders such a key through the label of the `ModelName`. A control without identities, and a command without marked properties, record and replay as they are.

The ids of a property may belong to another control than the target: `@DisplayedObjectId(control = "source")` names the argument property holding the reference of that control, a `String` that is its control id as the browser sends it or its semantic address. The recorder replaces the reference by the address of the control (`ScriptingSession.addressOf`) and the ids by keys through the identities of that control; the replay resolves the address back to the control (`ScriptingSession.controlOf`, a `ControlReferences`), dispatches its id and resolves the keys through its identities. A reference naming no control of the window - a drag from another window - leaves the reference and its ids as they are.

**Drag and drop.** `drop {source, keys, selection, targetKey, zone}` is the one drop command of the browser, the agent and a replay: `source` is the control the drag started in, `keys` the ids of the dragged items in that control (`@DisplayedObjectId(control = "source")`, a JSON array), `targetKey` the id of the row, node, card or column of the receiving control it was made on (`@DisplayedObjectId`). A recorded drop therefore names the source by its address, the dragged objects by their keys in the source and the target by its key in the receiving control, and replays at the same place in another session; a dragged object or a target that is no longer displayed fails the replay with "The object is not displayed". An agent names the source by the address it observes. With `selection: true` the drag carries the source's current selection instead of the items `keys` names.

The projection is taken in one of two `ProjectionMode`s, handed through `scriptingScalarState(mode)`, `ScriptingNode.scriptingState(mode)` and the identity helpers (`ScriptingModelKey.putIdentity`, `ItemSelection.identifyItem` / `identifyItems` / `identifyKeys`):

- `AGENT` (`observe()`): an object of a control offering identities is projected by its id under `id` (`ScriptingModelKey.ID`), with its `label` - the id its commands take. Every control uses this one name - a table row, a tree node, a board card and column, a dropdown option and value element, an item of a selectable list -, whatever property its client state carries the id in (`value` of an option, `key` of a card). The objects of any other control are projected by key.
- `KEY` (`ScriptingTreeProjector.nodeState`, the UI inspector, assertions): every object by its key, so the state holds in every session.

Addresses do not depend on the mode, except the segments of items (rows, tree nodes, cards), which identify the item as the mode identifies objects: by id in `AGENT`, by key in `KEY`.

## Actions

A node's actions are its `@ReactCommandHandler` commands minus the ones that are UI chrome rather than user intent, and minus the ones that are not executable in the control's current state (see [What the observation contains](#what-the-observation-contains)). A command is chrome when its handler says `technical = true` (closing a snackbar, popping out a panel, reporting a display class) or when the control lists it in `scriptingHiddenCommands()`. Chrome is neither advertised nor recorded; `nonRecordableCommands()` adds commands that are advertised but not recorded (scrolling, column resizing).

Each action carries the schema of its arguments:

- **Typed arguments.** A handler declares a `ReactCommand` subtype as its argument parameter instead of a raw `Map`. The client's JSON arguments are bound into it through `JsonConfigurationReader` (by the `@Name`s of the properties), and the handler reads getters. The interface is at the same time the advertised JSON schema (`argsSchema`, built by `JsonConfigSchemaBuilder`, with `@Mandatory`, types and the generated property labels; the envelope properties `address`, `name` and `target` are stripped, and the schema is merged into one plain object schema of the interface with all inherited properties, without the `$type` tag), the human-readable description of a recorded step (its `@Label` is the template, e.g. `Activate tab '{tabId}'`, rendered by `ReactCommands.describe` through `ConfigLabelProvider`) and the recorded step itself. `ReactCommandMap` rejects an argument interface that does not extend `ReactCommand`.
- **Raw maps.** The configuration JSON reader binds a list of primitive values only through `@JsonBinding(SimpleJsonListBinding.class)` (the option ids of the dropdown's `SelectValueArguments`), and no map with arbitrary keys. The few commands taking such arguments (`paletteChanged` of the color input, `reorder` of the dashboard, `updateSizes` of the split panel) keep a `Map` and describe it with `@ReactParam` in `@ReactCommandHandler(params = ...)`. The projection turns the parameters into an object schema (`ArgsSchema.forParams`: a property per parameter with its type and description, the required ones in `required`), listed under the id `<control class>.<command>` like a typed schema. A `ScriptingNode` declaring its own actions builds its schema the same way from `ScriptingParam`s.

`ScriptingNode` is an optional interface for a control that replaces its whole projected state (`scriptingState(mode)`) or action list (`scriptingActions()`); returning `null` keeps the generic derivation.

## Acting is acting as the user

A headless command takes the path a browser command takes, so it is subject to the same checks. `ScriptingSession.execute` first refuses a command whose `scriptingCommandState(command)` is not executable - the actions the observation does not advertise. The handler checks again, since the client offering a command is no check either: the browser may be bypassed. A handler therefore refuses what the user interface does not offer, whatever arrives: no write to a field that is not editable, no press of a hidden or disabled button or menu entry (the `CommandModel` decides), no navigation to a hidden sidebar item, no form lifecycle command outside its edit state. A refusal is a `TopLogicException` with a message (`CommandErrors.notExecutable(ExecutableState)` for a command that is not offered), which reaches the consumer as a failed step.

A field drops the input of the browser rendering it silently while it does not accept input, since that browser may lag behind the server (an editor flushing its content on blur after the interaction left edit mode); the same input from a headless dispatch is refused with "The field cannot be edited." (`ReactFormFieldControl.refuseInput`, deciding by `ReactControl.isClientDispatch()`).

**Echo of a command's state.** A handler may record a state change silently (`updateStateSilently`) because the browser that sent the command already shows it - the value typed into an input, a size dragged by the user. That holds only for a command from the browser. `ReactServlet` dispatches browser commands through `executeClientCommand`; every other caller - `ScriptingSession.act`, a replay, server code - uses `executeCommand`, which sends the control's full state after the command whenever the handler left silent changes behind. A handler needs no logic of its own for where a command came from.

## The script recorder

Each window has a `ScriptRecorder` on its `SSEUpdateQueue` (`queue.getRecorder()`). `start()` begins a fresh recording, discarding the previous steps; `stop()` ends it and keeps the steps until the next start; `steps()` is a snapshot copy.

While recording, `ReactServlet` feeds every command the browser dispatches into the recorder, before the command runs (`ScriptRecorder.capture(root, control, command, arguments)`):

1. A command for which `isRecordable(command)` is false is skipped.
2. `recordCommand(command, arguments)` lets the control translate the command into a replay-stable `RecordedCommand`. The default records the command as its typed item. A control whose arguments are bound to the session overrides it:
   - The tree records its node gestures, the table its row gestures (`select` with and without `Ctrl` or `Shift`, `activate`, `expand`), the dropdown `valueChanged`, as they are dispatched: the node, row and option ids are `@DisplayedObjectId`s, which the recorder replaces by the keys of their objects (see "Object ids and keys"). The table's `selectAll` and keyboard navigation (`moveSelection`) name no row and are recorded as they are; they replay on the rows, the cursor and the range anchor the steps before them leave.
   - The tree, the table and the board record a drop as it is dispatched: the source control by its address, the dragged and the target item by their keys (see "Object ids and keys").
   - A gesture on an object without a name is recorded verbatim.
3. The step gets the control's address (`addressOf`) and is recorded.

A `RecordedCommand` marked `coalescing` replaces the previous step if that one has the same address and command, so the keystrokes of one field edit end up as one step with the final value. The recorder merges by address and command only and knows nothing about controls. A command dispatched headlessly (`act`, replay) does not pass `ReactServlet` and is not recorded.

An **assertion** is a step, too: `ScriptRecorder.recordAssertion(address, expectedState)` appends an `AssertCommand` (the pseudo-command `assertState`) carrying a subset of the node's projected state. On replay it is verified instead of dispatched: `AssertCommand.mismatchingKeys(expected, actual)` compares the expected entries with the node's current state (`ScriptingTreeProjector.nodeState`) by canonical JSON, map by map, and reports the paths of the entries that differ. State the assertion does not name is ignored.

`ScriptingSession.replay(step)` replays one recorded step in a window tree - an assertion is verified, any other step dispatched to the control at its address; `ReactWindowReplay.act` runs it in the window's interaction. A step whose address no longer resolves throws an `IllegalArgumentException` with the address; a step whose key no longer resolves, and an assertion that does not hold, throw a `TopLogicException` with its message (`ReactWindowReplay.act` throws it once the window has settled the state the step left behind). `TestCrossSessionReplay` records navigation, a tab switch, row clicks with and without modifiers, a tree expansion and selection, a dropdown choice, field input and an assertion in one session and replays them in a fresh one, comparing the whole projection of both sessions after every step.

The recorder is observable (`addListener`): the listener is called after every start, stop and capture, outside the recorder's monitor. A recorder side-window reflects the steps of the recorder of its opener window this way, live over its own SSE connection.

A recording lives in memory, in the window it was recorded in. It is a list of `ReactCommand` items; the description, the arguments for dispatch (`ReactCommands.arguments`) and the wire form of the agent endpoint are computed from the item.

## Making a control well-addressable

A new control is addressable without any of this, but the generic derivation produces addresses and observations only as good as its state. Check:

- **A stable name.** If the label a user sees is not a stable identity - it is localized, changes with the edit state or names mutable state such as the active tab - override `scriptingName()` with the technical identity (a form field's attribute name, a command's id). Never name a container after its selection.
- **A meaningful role.** Override `scriptingRole()` where the React module name is not what the node is.
- **Structure only?** A control that only arranges its children returns `true` from `scriptingTransparent()`.
- **Selection-driven content?** A container that swaps its content by a selection returns a slot from `scriptingChildSlot(child)` for the content child, named by the configuration id of the selected entry.
- **No noise.** List rendering-only state keys (padding, variant, icon, debounce, CSS class) in `scriptingPresentationKeys()`, extending the inherited set with `presentationKeys(super.scriptingPresentationKeys(), ...)`. `null` values and child controls are left out automatically.
- **Observations about the control** that are not for the user (why rows are missing, how a value came about) go to `putDiagnostic(key, value)`: projected under `diagnostics`, never sent to the browser.
- **Commands.** Mark chrome handlers `technical = true`. Give every other handler a typed `ReactCommand` argument interface with a `@Label` that reads as a step description, and mandatory properties marked `@Mandatory`. Refuse in the handler what the UI does not offer, and say the same in `scriptingCommandState(command)`, so that the command is advertised only where the UI offers it.
- **Shown at all?** A control that renders itself but is not seen in some state answers `false` from `scriptingVisible()`; a container rendering children it does not show narrows `visibleChildren()`.
- **Items with controls.** A container displaying controls for its rows, cards or entries, whose texts its own state already carries, returns them from `scriptingItems()` (role, id from its `objectIdentities()`, object, controls) and leaves them out of `scriptingChildren()`.
- **Session-bound arguments.** If a command's arguments are ids of displayed objects, keep the ids in an `ObjectIdIndex`, offer it through `objectIdentities()` and mark the id properties `@DisplayedObjectId` (as the dropdown's `SelectValueArguments`, the table's `SelectRowArguments`): the recorder and the replay translate them, see "Object ids and keys". Never let a command address an object by its position: the positions move under a gesture in flight. Mark per-keystroke commands `coalescing`.
- **Data in the projection.** A control whose state holds only child controls or client-side ids projects nothing a consumer can read. Override `scriptingScalarState()` to add a readable form - the table adds `rows`, each with its identity (`id` and `label` in `AGENT` mode, the business `key` in `KEY` mode), `selected` and the cell texts, bounded to the current viewport (at most 100 rows, `totalRowCount` telling how many rows the table displays); in a tree table or a grouped table each row also carries `depth`, `expandable` and, if expandable, `expanded`, and a group header the value of its group as the text of its first cell (`TableView.groupText`) and its size as `groupCount`; the tree adds its displayed `nodes`, the wizard the `currentStep` of the `stepCount` its counter shows. What the user reads off a control belongs in its state even where the client draws it - the bounds and the step of a slider.
- **No session ids in the projection.** Project an object by its key (`ScriptingModelKey.putIdentity`), not by an id allocated in the session, and list client wiring that names other controls by id in `scriptingPresentationKeys()`.

## Pitfalls

- **Sibling indexes are positional.** `button#3` changes when the siblings reorder, and when a sibling becomes visible or invisible. Rows and options are reached by id or key, not by index.
- **An observation is a snapshot.** It reflects the tree when it was taken; a later change shows up only in a new observation.
- **Observing holds the session.** An observation is taken within the session's interaction, so a browser command of the same session waits while a large tree is projected (including the label of every model).
- **Labels may change between sessions.** A name derived from a localized label resolves only in a session with the same locale; a control that is to be addressed reliably names itself by its technical identity.
- **Recorded arguments must be replay-stable.** A command recorded verbatim with session ids or positions - a gesture on an object without a name, which the controls record verbatim - replays only in the same state of the same session.
