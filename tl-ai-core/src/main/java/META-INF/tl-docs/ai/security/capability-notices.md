# Capability notices

Filtering the tool schemas leaves the model unable to tell "you are not permitted" from "that skill is not loaded yet" from "that does not exist": all three look like absence, so the agent answers the user with a vague "I can't do that" or goes hunting for a skill it may not use either. The mechanisms below make the absence legible. **They are UX, not a control**: the gates are the deterministic Java checks of [tool authorization](doc:ai/security/tool-authorization); a principal who holds every capability its tools require is told exactly that rather than given a list of gaps. `AgentCapabilities` (package `com.top_logic.tl.ai.core.agent`) is the one place they are computed.

## Skills and delegates the user cannot use are not offered

- **A skill whose every tool is denied is not offered** (`AgentFactory.injectSkills`, `buildDynamicSkillTool`, all through `AgentCapabilities.unusableReason`). A skill with no tools at all is pure instruction text and is kept; a partly denied skill is kept and loads only the permitted subset; a skill whose tool names do not resolve is kept, because a typo is not a denial. Every dropped skill is logged at INFO with the deciding reason - silent capability loss is the failure mode this must not have.
- **A delegate whose every reachable tool is denied is not offered** (`AgentCapabilities.unusableReason(AgentDefinition)`). A delegate's effective tool set is its own `<tools>` **plus** every tool of every skill it declares **plus** its MCP servers' tools **plus**, transitively, everything its own delegates reach (`reachableTools`). The walk visits each agent once, so a delegation cycle terminates. Three cases keep a delegate: one that reaches no tool at all (a delegation-only agent), one that is partly reachable, and one whose tool names resolve nowhere. Every dropped delegate is logged at INFO naming the capabilities it needed. A principal who may use every tool loses nothing - the generated `### Available Delegates` section is then byte-identical to the unfiltered one (`TestDelegateFilter.testCatalogOfAPrincipalWhoMayUseEverything`).

  All three exposure surfaces filter from the one judged list (`AgentFactory.delegateOffers`), so they cannot drift: the prompt catalog (`delegateCatalog`), the `delegate_to_*` registration in both catalog paths (`registerDelegationTools`, static and dynamic), and `list_agents` (`ListAgentsTool.execute`). Filtering only the prompt text would be cosmetic - the model can call a tool the prompt never mentioned. With no delegate left, `wait_for_subagent` is not wired in either. This takes nothing from anyone: a child inherits the parent's `SecurityContext`, so a delegate whose every tool is denied could only ever have started, filtered its own schemas to nothing, spent a provider round trip and reported failure.

  **A partly reachable delegate stays, and is marked as limited.** It can do part of the job, so it is offered, and the catalog line under it names the capabilities it *cannot* use, in the register of the capability notice below (`Limited for this user - it cannot use: ...`, each capability with its group description); `list_agents` says the same in its `cannotUse` field. Offering it silently would make the parent discover the limit by sending work that comes back refused; dropping it would remove a capability the user actually holds. A delegate the principal can use in full is not annotated.

## A spawn or delegation that could only fail is refused

`spawn_subagent` names its target at call time, so there is no list to leave it out of: `SubagentSpawner.detachedSpawnRefusal` applies the same predicate to the name the model asked for, and the answer is an ordinary tool error rather than an exception, because what the user has to hear is which capability to ask for. `list_agents`, which feeds the spawn decision, filters the same way, so the two surfaces agree.

**It is judged against the context the child will get.** A detached spawn is a background run, so the predicate is asked of `security().withBackgroundCeiling()`: an agent the parent turn reaches in full can be out of reach once the allowlist applies, and that case is refused with the unattended wording - *"A spawned subagent runs unattended ... it cannot reach the capabilities its tools require, even though this user holds them"*. Telling a user they lack a right they do hold would send them to their administrator for the wrong change; the split is `AgentCapabilities.lostToBackgroundCeiling`, which the capability notice uses as well.

A **synchronous** delegation refuses the same way, in `DelegationTool.delegationRefusal`, asked of the parent turn's own context (which is what the child inherits) and without the unattended wording. Neither refusal ever says or implies that the agent does not exist - it does, and a model told otherwise looks for another name for the same work. An agent that really is unknown is not refused here: that is not a denial.

**Which grant to ask for depends on what refused.** `AgentCapabilities.unusableReason(AgentDefinition)` answers an `Unusable` - a cause plus the message - and the refusals compose capability text only for `Unusable.Cause.NO_REACHABLE_TOOL`. For the causes that are not about capabilities - `<agent-access>` withholding the agent, the agent being `infrastructure`, the agent's own model or MCP server being denied - they relay `RoleAccessPolicy.Decision.Denied#message()`, which names the setting an administrator would change. `Unusable.Cause.TYPE_UNREADABLE` - every tool the thing reaches works on model types the account may not read - names a Read grant on the type ([declared types](doc:ai/security/declared-types)). `TestSpawnFilter`, `TestAgentGate`, `TestCapabilityDeclaredTypes` and, on the deployed policy, `SecDemoSpawnFilterTest` pin it.

## Absence says which absence it is

- **`loadSkill` advertises only the tools the principal can call** (`SkillTool.addSkillTools`), so an authoritative tool result does not contradict the tool list of the next turn.
- **A `loadSkill` for a skill that is not there says which absence it is** (`AgentCapabilities.skillAbsenceReason`, wired in `AgentFactory.absenceReason`). A skill this agent declares and the acting user may use nothing in is *withheld from the current user*, naming the capabilities its tools require. The same skill in an **unattended** run, where the `<background-allowlist>` removed it (`SecurityContext.withheldByBackgroundCeiling` → `AgentCapabilities.lostToBackgroundCeiling`), says *this run is unattended* instead. A skill the application has and this agent does not declare says so and names an administrator, without a capability. An id that resolves nowhere keeps the plain "not available for this agent" with the list of loadable skills, so a typo discloses nothing. Each permission case ends with the sentence against guessing that the notice below carries.
- **A call for an absent tool says which absence it is** (`ToolCatalog.absenceReason`). A name no skill declares and no registry knows stays `Unknown tool` with the permitted-only list. A name one of the agent's own skills declares is answered with "load that skill". A name the service registry resolves but the agent carries nowhere - a TL-Script tool no agent lists - says so, and that an administrator would have to add it to the agent or to a skill. `DynamicToolCatalog.setReachableBySkill` separates the skill case from the not-carried case; it is used for the message only, never for lookup. A capability *is* named where the application really has the tool and the acting user really is denied it - that is the ordinary denial reason. A name that resolves nowhere never goes through the permission check, so a typo cannot make the answer disclose which capabilities the user lacks.
- **A skill's description does not point at a skill the reader cannot load.** Where the referring skill can carry the tool its guidance depends on, it does, and the filter drops the pair together: `TL_writingDataChanges` declares `changeData` itself. A guidance-only skill declares no tools and always survives the filter. Where the referenced skill belongs to a different domain (`TL_agenticAuthoring` → `TL_writingDataChanges`), the description says what to do when the reference is unreachable. `TestFrameworkSkillReferences` fails on a cross-reference that does neither.

## `listTools`: the agent can ask what it carries

Every message above answers a question the model *stumbled into*. None answers the question a user asks directly: *"can you use `X`?"* `listTools` (`ListToolsTool`, injected by `AgentFactory.listToolsTool`) is the source: this agent's own tools, every skill it declares with what a load would hand over, and the capability behind each withheld entry (`AgentCapabilities.unusableReason(Tool)`, quiet, so enumerating a catalog writes no audit line for calls nobody made).

It is self-inspection only, and never withholdable. It answers "what do *I* carry", never "what does this application have" - that is registry-wide inspection and stays behind `agent.meta`. Its group `introspection` is in `RoleToolAccess.IMPLICIT_BASELINE`, so it reaches every role and every run without a `<baseline>` entry, unattended runs included; an explicit `<deny>` still wins. It is injected into every agent's catalog rather than declared in `<tools>`, like `loadSkill`: it is a property of being an agent. It discloses nothing new - every entry is filtered for the acting user, and a withheld entry names the capability the notice below names in the system prompt.

## The capability notice in the prompt

The generated skill catalog names the capabilities the principal lacks (`AgentCapabilities.notice`), computed from the tools *this agent* can reach - its own `<tools>` plus its skills' - rather than from every group in the deployment. A denied capability costs one short line instead of a full JSON schema, and the agent can name it to the user. Each name carries the group's one-sentence description (`ToolGroups.labelKey`), because a group named without one invites the model to guess from the name. The section also states the three absences and tells the agent not to blame a capability unless the message it got names one - and every message that *does* name one closes by saying which subject those names belong to (`AgentCapabilities.NO_GUESSING`).

The notice does not depend on whether the agent declares skills: an agent with neither skills nor anything to report gets nothing at all - no empty heading - and every other agent gets its notice, including whether its own run is unattended.
